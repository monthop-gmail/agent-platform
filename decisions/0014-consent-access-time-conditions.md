# ADR-0014: `consent/v1` — เงื่อนไขที่ต้องยังเป็นจริง "ตอนเข้าถึง" ไม่ใช่แค่ตอนออกใบ

**Status:** Accepted (2026-08-21)
**Date:** 2026-08-21
**Depends on:** [ADR-0012](0012-consent-contract.md) · [ADR-0007](0007-multi-tenancy.md) · [ADR-0006](0006-contract-versioning.md)
**Blocking:** [issue #25](https://github.com/monthop-gmail/agent-platform/issues/25) · `contracts/consent/v1/consent.schema.yaml`

## Context

[`care-agent-platform`](https://github.com/monthop-gmail/care-agent-platform) พบระหว่างทำ multi-organization (M6) ว่า `consent/v1` ตอบได้ว่าใบยังใช้ได้ไหมจาก **สองอย่างเท่านั้น** — `revoked_at` และ `expires_at` — ซึ่งทั้งคู่เป็นเหตุการณ์ที่ต้องมีคนหรือเวลามาทำให้เกิด

แต่ใบยินยอมจำนวนหนึ่งผูกกับ **ข้อเท็จจริงที่เปลี่ยนได้เองโดยไม่มีใครไปแตะใบ**:

> ครอบครัวอนุญาตให้ "หมอสมชาย **ในฐานะแพทย์ของโรงพยาบาล A**" อ่านข้อมูลผู้ป่วย
> วันหนึ่งหมอสมชายลาออกไปโรงพยาบาลอื่น

ณ วินาทีนั้นใบยินยอมยังไม่ถูกเพิกถอน (ไม่มีใครรู้ว่าเขาลาออก) และยังไม่หมดอายุ (ตั้งไว้ 1 ปี) → **ยังใช้ได้ตาม contract** ทั้งที่เงื่อนไขที่ครอบครัวยินยอมไม่เป็นจริงแล้ว

สิ่งที่ครอบครัวยินยอมคือ *"หมอในฐานะแพทย์ของโรงพยาบาลนั้น"* ไม่ใช่ *"คนคนนี้ในฐานะบุคคล"* — **ความต่างนี้ไม่มีที่อยู่ใน schema ปัจจุบัน**

### ทางออกที่ contract ปัจจุบันเปิดให้ทำ — แย่กว่าทุกทาง

| ทาง | ทำไมไม่พอ |
| --- | --- |
| ตั้ง `expires_at` สั้น ๆ แล้วต่ออายุบ่อย | ช่องโหว่ยาวเท่าหน้าต่างที่เหลือ · และผลักภาระไปที่เจ้าของข้อมูลที่ไม่มีทางรู้ว่าหมอลาออกเมื่อไร |
| ให้ระบบไล่เพิกถอนเองเมื่อรู้ว่าคนลาออก | ต้องมี job ไล่ทุกใบ · ระหว่างที่ job ยังไม่รันสิทธิ์ยังเปิด · และ **`revoked_at` จะโกหก** ว่ามีคนเพิกถอนทั้งที่ไม่มีใครตัดสินใจอะไร |
| ให้ `grantee` เป็นองค์กรแทนคน | พนักงานที่เข้าใหม่พรุ่งนี้ได้สิทธิ์ทันทีโดยเจ้าของข้อมูลไม่รู้ตัว — **แย่กว่าปัญหาเดิม** และขัด `consent_rules` ข้อ "ความสัมพันธ์ไม่ให้สิทธิ์อะไรโดยอัตโนมัติ" |

### จุดที่เปลี่ยนธรรมชาติของ contract — และเป็นเหตุผลว่าทำไมต้องเคาะที่นี่

ทุกวันนี้ `consent/v1` มีคุณสมบัติที่ไม่มีใครเขียนไว้แต่ทุกคนพึ่งอยู่: **อ่าน payload ใบเดียวก็ตอบได้ว่าใบนี้ใช้ได้ไหม** เพราะทั้ง `revoked_at` และ `expires_at` อยู่ในใบ

การเพิ่มเงื่อนไขทำให้คุณสมบัตินี้หายไป — ความถูกต้องของใบขึ้นกับ **สถานะที่อยู่นอก payload**

```text
เดิม:  valid = ยังไม่ revoke ∧ ยังไม่หมดอายุ            → ตอบได้จากใบเดียว
ใหม่:  valid = ยังไม่ revoke ∧ ยังไม่หมดอายุ ∧ ∀c ∈ conditions: c ยังจริง
                                                        → ต้องถามระบบอื่นเสมอ
```

นี่ไม่ใช่ผลข้างเคียงที่ต้องกลบ — มันคือ **การพูดความจริง** ว่าใบนั้นไม่เคยใช้ได้ลอย ๆ อยู่แล้ว แต่ต้องเขียนลงสัญญาให้ชัด ไม่งั้นจะมี consumer ที่ cache ผล "valid" ไว้ตามอายุใบ ซึ่งเป็นบั๊กที่ payload หน้าตาเหมือนกันเป๊ะจากภายนอก

### ฝั่ง `care-agent-platform` ทำไปแล้ว — และนั่นคือเหตุผลที่ต้องรีบเคาะ

เขา implement แล้วใช้จริง มีเทส S16/S17 ครอบ ([ADR-0010](https://github.com/monthop-gmail/care-agent-platform/blob/main/decisions/0010-organizations-are-not-tenants.md)) — `has_consent()` ตรวจ `revoked_at` → `expires_at` → **แล้วตรวจ conditions ทุกข้อ** · โมดูล consent ไม่รู้ว่าเงื่อนไขแต่ละชนิดแปลว่าอะไร โดเมนลงทะเบียนตัวตรวจเอง · fail closed ทุกทาง · และ **payload ที่ส่งออกมี `conditions` ติดไปด้วยแล้ว**

`consent/v1` ไม่ได้ตั้ง `additionalProperties: false` — field นี้จึง valid เงียบ ๆ อยู่ตอนนี้ สถานการณ์เดียวกับ `supersedes_decision_id` ใน [ADR-0013](0013-approval-supersedes-chain.md): **field อยู่บน wire แล้วไม่ว่าเราจะรับหรือไม่** สิ่งที่เลือกได้คือมันจะเป็นของกลางที่นิยามไว้ หรือเป็นของ repo เดียวที่ consumer รายที่สองลอกไปโดยไม่รู้ว่าไม่ใช่ของกลาง

## เกณฑ์ 4 ข้อของ ADR-0012 — ผ่านหรือไม่

เกณฑ์ชุดนี้เขียนไว้สำหรับ **รับ contract ใหม่** ไม่ใช่สำหรับขยาย contract เดิม แต่ประเมินตรง ๆ ไว้เพื่อไม่ให้ "ขยายของเดิม" กลายเป็นทางลัดที่เลี่ยงเกณฑ์:

| # | เกณฑ์ | ผล |
| --- | --- | --- |
| 1 | มี contract เดิมตอบได้ไหม — ถ้ามีให้ขยายตัวนั้น | ✅ **นี่คือการขยายตัวเดิม** ตามเกณฑ์ข้อนี้เอง |
| 2 | consumer ≥ 2 ราย หรือ 1 รายใช้จริง + รายที่สองระบุตัวได้ | ⚠️ **ข้อที่อ่อนที่สุด** — วันนี้มี `care-agent-platform` รายเดียว · `devfactory-core` ไม่มีความต้องการนี้ |
| 3 | มี implementation จริงให้อ้าง | ✅ M6 core (PR #12) + เทส S16/S17 + ADR-0010 ฝั่งเขา |
| 4 | platform เข้าใจ semantics พอจะเป็นผู้ตัดสินสุดท้าย | ✅ `consent/v1` platform ถือ semantics เองอยู่แล้ว ([ADR-0012 D1](0012-consent-contract.md)) — ไม่มีข้อพิพาท authority |

**ข้อ 2 ไม่ผ่านแบบเต็ม และไม่ควรแกล้งว่าผ่าน** สิ่งที่ชดเชยคือ:

* สิ่งที่ขอไม่ใช่ *vocabulary ของโดเมน* (ซึ่งต้องรอรายที่สองเพื่อพิสูจน์ว่า general) แต่เป็น **ช่องเปล่าที่ platform ไม่ตีความ** — รายที่สองจะเติมคำของตัวเองได้โดยไม่ต้องแก้ schema
* ต้นทุนของการรอไม่เป็นศูนย์ — payload ที่ใช้ชื่อนอกสัญญากำลังสะสมอยู่แล้ววันนี้

## สิ่งที่ต้องเคาะมี 3 ชั้น

1. **รับหรือไม่รับ** ว่าเงื่อนไขระดับเข้าถึงเป็นเรื่องของ `consent/v1`
2. **รูปของแต่ละเงื่อนไข** — namespace ของ field ในนั้นเป็นของใคร
3. **กติกาที่ต้องมาพร้อมกัน** — เพราะ field เปล่า ๆ ที่ไม่มีกฎกำกับจะถูก implement ผิดทางแน่นอน

## Options

### A. รับ — `conditions` แบบที่เสนอมา (field ของโดเมนวางเรียงข้าง `kind`)

```yaml
conditions:
  - kind: org_membership
    organization_id: org-abc123
```

* ✅ ตรงกับสิ่งที่ `care-agent-platform` ใช้อยู่จริง — รับแล้วจบ ไม่ต้อง migrate
* ✅ อ่านง่ายที่สุด
* ❌ **namespace ปนกัน** — วันที่ platform อยากเพิ่ม field กลาง (เช่น `description` สำหรับหน้าจอ audit) มันจะชนกับ key ของโดเมนที่มีคนใช้ไปแล้ว และไม่มีทางเพิ่มแบบ additive อีก
* ❌ ขัดกับนิสัยของ repo นี้ที่ให้ข้อมูลรูปร่างโดเมนอยู่ในกล่องที่มีชื่อ (`event/v1.metadata` · `policy/v1.constraint`)

### B. รับ — `kind` + `params` · ปิด `additionalProperties` ที่ตัวเงื่อนไข ⭐

```yaml
conditions:
  - kind: org_membership
    params:
      organization_id: org-abc123
```

* ✅ **แบ่ง namespace ชัด** — ชั้นนอกเป็นของ platform (เพิ่ม field ใหม่ได้แบบ additive ตลอดไป) ชั้น `params` เป็นของโดเมน (platform ไม่แตะ ไม่ตีความ)
* ✅ `additionalProperties: false` ที่ตัวเงื่อนไขทำให้ **key ที่พิมพ์ผิดในชั้นนอกโดนจับ** — ตรงข้ามกับกับดักที่ `devfactory-core` บันทึกไว้เองว่า "field ที่เราตั้งชื่อเองจึง valid เงียบ ๆ"
* ✅ สอดคล้องกับ `event/v1` และ `policy/v1` ที่ทำแบบเดียวกันมาก่อน
* ❌ `care-agent-platform` ต้อง migrate หนึ่งชั้น (payload + ตัวตรวจ) — เขาเสนอจะส่ง PR เองอยู่แล้ว และเคยรับ rename มาแล้วในเคส [#22](https://github.com/monthop-gmail/agent-platform/issues/22)
* ❌ `params` ยังเปิด — key ที่พิมพ์ผิด *ในนั้น* ยังเงียบเหมือนเดิม (แต่นั่นเป็นของโดเมน ไม่ใช่ของ platform ที่จะตรวจให้)

### C. ไม่รับ — ให้ `policy/v1` ตรวจสมาชิกภาพแทน

`policy/v1` ตอบ *"identity นี้ทำ action นี้ได้ไหม"* และประเมินข้อเท็จจริงสด ๆ ได้อยู่แล้ว จึงเช็ค org membership ได้โดยไม่ต้องแตะ consent

* ✅ ไม่ต้องแก้ contract เลย · ด่านสองด่านยังทำงานเหมือนเดิม
* ❌ **ทำให้บันทึกว่า "เจ้าของข้อมูลยินยอมอะไร" ผิดความจริง** — ครอบครัวยินยอม *"หมอในฐานะแพทย์ของ รพ. A"* แต่ใบจะเขียนว่ายินยอมให้ *"หมอสมชาย"* เฉย ๆ
* ❌ **เงื่อนไขจะกลายเป็นกฎของผู้ควบคุมข้อมูล ไม่ใช่ของเจ้าของข้อมูล** — วันที่ใครแก้ policy ขอบเขตที่ *ดูเหมือน* เจ้าของยินยอมจะกว้างขึ้นเงียบ ๆ โดยไม่มีใครไปแตะใบ ซึ่งเป็นสิ่งที่ ADR-0012 ตั้ง contract นี้ขึ้นมาเพื่อกันโดยเฉพาะ
* ❌ ตอน audit ย้อนหลังจะแยกไม่ออกว่า "เข้าไม่ได้เพราะเจ้าของไม่ยอม" กับ "เข้าไม่ได้เพราะกฎองค์กร" — คนละเรื่องกันในเชิงกฎหมาย

### D. ไม่รับ — ใช้ `expires_at` สั้น ๆ แล้วต่ออายุ

* ✅ ใช้ของที่มีอยู่
* ❌ ช่องโหว่ยาวเท่าหน้าต่าง และผลักภาระการรู้ข้อเท็จจริงไปที่คนที่ไม่มีทางรู้ (ดูตารางข้างบน)

### E. ไม่รับ — ให้ `grantee` เป็นองค์กร

* ❌ พนักงานใหม่ได้สิทธิ์ทันทีโดยเจ้าของไม่รู้ตัว · การเพิกถอนกลายเป็นการตัดทั้งองค์กรซึ่งไม่มีใครกล้าทำ

### F. รับ แต่ platform กำหนด `kind` เป็น enum ปิด

* ✅ ตรวจได้ด้วย schema ว่าไม่มี kind แปลกปลอม
* ❌ **ทำซ้ำความผิดพลาดของ [#17](https://github.com/monthop-gmail/agent-platform/issues/17)** เป๊ะ ๆ — enum ปิดที่ platform ไม่มีทางรู้ค่าทั้งหมด · `sighting`, `shift_active`, `contract_in_force` ล้วนเป็นคำของโดเมนที่เราไม่รู้จัก
* ❌ platform จะกลายเป็นคอขวดของทุกเงื่อนไขใหม่ ทั้งที่ประกาศไว้เองว่าไม่รู้จักโดเมน

### เรื่องชื่อ field — `conditions` กับ `valid_while`

`valid_while` บอกกติกาไว้ในชื่อตัวเอง (ต้องจริง *ตลอดเวลาที่ใช้*) ส่วน `conditions` อ่านได้สองแบบ และแบบที่ผิดคือ *"เงื่อนไขที่บันทึกไว้ตอนออกใบ"* — ซึ่งบังเอิญเป็นความเข้าใจผิดที่ ADR ฉบับนี้มีอยู่เพื่อกัน

เลือก `conditions` เพราะ: เป็นชื่อที่ implementation จริงและ issue ใช้อยู่แล้ว · ไม่ได้ *ผิด* แบบ `supersedes_decision_id` ที่ชี้ไปคนละสิ่งกับค่าที่ใส่ · และความกำกวมปิดได้ด้วยกฎที่บังคับใน `consent_rules` ซึ่งบังคับแรงกว่าชื่อ field อยู่แล้ว

## กติกาที่ต้องมาพร้อม field — ไม่ใช่ทางเลือก

field เปล่า ๆ ที่ไม่มีกฎกำกับจะถูก implement ผิดแน่นอน · กฎเหล่านี้คือสิ่งที่ทำให้เรื่องนี้เป็นของ platform ตั้งแต่แรก (*vocabulary* เป็นของโดเมน แต่ *กติกาว่าเงื่อนไขต้องถูกตรวจทุกครั้ง* เป็นระดับเดียวกับ "การเพิกถอนมีผลทันที" ที่อยู่ในสัญญาแล้ว):

| กฎ | ทำไม |
| --- | --- |
| เงื่อนไขต้องถูกตรวจ **ทุกครั้งที่ใช้** ไม่ใช่แค่ตอนออกใบ | เป็นเหตุผลทั้งหมดที่ field นี้มีอยู่ |
| `kind` ที่ไม่รู้จัก = **ไม่อนุญาต** | หลักเดียวกับ scope ที่ไม่รู้จักใน `platform_rules` ปัจจุบัน |
| ตัวตรวจที่ error = **ไม่อนุญาต** ไม่ใช่ปล่อยผ่าน | fail closed — ระบบที่ล่มไม่ควรกลายเป็นระบบที่เปิดกว้าง |
| **ออกใบที่มีเงื่อนไขซึ่งระบบนั้นตรวจไม่ได้ไม่ได้** | ใบที่ตรวจไม่ได้จะใช้ไม่ได้เลยตอน runtime อยู่ดี — ปฏิเสธตอนออกใบดีกว่าให้เจ้าของข้อมูลเข้าใจว่าเขาให้สิทธิ์อะไรไปแล้ว |
| เงื่อนไข **narrow ได้อย่างเดียว** ห้ามขยายสิทธิ์ | ทั้งชุดต่อกันด้วย AND · เงื่อนไขที่ *ให้* สิทธิ์คือ scope ที่ปลอมตัวมา |
| ใบที่มี `conditions` **ไม่ self-contained** — ห้าม cache ผล valid ตามอายุใบ | ความถูกต้องอยู่นอก payload แล้ว |
| **ไม่มี `conditions` = ไม่มีเงื่อนไข** · `[]` ใช้ไม่ได้ (`minItems: 1`) | หลักเดียวกับ `expires_at: null` — ห้ามมีสองวิธีเขียนสิ่งเดียวกัน และห้ามมีสถานะที่สาม |
| `conditions` เป็น immutable เหมือน field อื่น — เปลี่ยนเงื่อนไข = ใบใหม่ | ตาม `platform_rules` ข้อที่มีอยู่แล้ว |

### สิ่งที่ตามมาที่ต้องเขียนไว้ตั้งแต่วันนี้ — audit ย้อนหลัง

เมื่อความถูกต้องอยู่นอก payload การ replay audit ปีหน้าจะตอบไม่ได้ว่า *"ตอนนั้นหมอยังสังกัดอยู่ไหม"* เพราะสถานะสมาชิกภาพเปลี่ยนไปแล้ว

ทางปิดคือ **event ของการใช้สิทธิ์ต้องบันทึกว่าเงื่อนไขถูกประเมินแล้วและผ่าน** ไม่ใช่บันทึกแค่ว่ามีการเข้าถึง — ซึ่ง `consent_rules` ข้อ 2 บังคับให้ออก audit event ทุกครั้งอยู่แล้ว แต่ยังไม่ได้ระบุว่าต้องมีอะไรในนั้น · **ADR นี้ไม่แก้ `event/v1`** เพียงบันทึกว่าช่องนี้เปิดอยู่และผูกกับ [issue #23](https://github.com/monthop-gmail/agent-platform/issues/23) ที่กำลังจะเคาะเรื่อง trail ที่ตรวจสอบได้

## Decision

**B** — เพิ่ม optional `conditions` เป็น array ของ `$defs.Condition` ที่มี `kind` (required, pattern ชุดเปิดแบบเดียวกับ `EventTypeName`) + `params` (optional object, โดเมนเป็นเจ้าของ) และ `additionalProperties: false` ที่ตัวเงื่อนไข · พร้อมกฎทั้ง 8 ข้อในตารางข้างบนลง `consent_rules` และ `platform_rules`

**Reason:** field นี้อยู่บน wire แล้ววันนี้ ([care-agent-platform PR #12](https://github.com/monthop-gmail/care-agent-platform/pull/12)) — ทางเลือกจริงคือ *นิยามมัน* หรือ *ปล่อยให้รายที่สองลอกของที่ไม่ใช่ของกลาง* ซึ่งเป็นบทเรียนเดียวกับ ADR-0013 · ปฏิเสธ C เพราะย้ายเงื่อนไขไปเป็นกฎของผู้ควบคุมข้อมูล ทำให้บันทึกความยินยอมผิดความจริงและกว้างขึ้นได้เงียบ ๆ · ปฏิเสธ F เพราะเป็น #17 ซ้ำ · เลือก B เหนือ A เพราะชั้นนอกต้องเป็นของ platform ไว้เพิ่ม field ทีหลังแบบ additive และเพราะ repo นี้ใส่ข้อมูลรูปร่างโดเมนไว้ในกล่องที่มีชื่อมาตลอด

**เกณฑ์ข้อ 2 รับทั้งที่ยังไม่ผ่านเต็ม — บันทึกไว้ว่าเป็นการตัดสินใจ ไม่ใช่การมองข้าม** · Platform Owner ชั่งแล้วว่าต้นทุนของการรอ (payload ที่ใช้ชื่อนอกสัญญาสะสมไปเรื่อย ๆ จนรายที่สองลอกไป) สูงกว่าความเสี่ยงของการรับเร็ว ซึ่งจำกัดอยู่แค่ **รูปของช่องเปล่าที่ platform ไม่ตีความ** ไม่ใช่ vocabulary ที่จะต้องมาแก้ทีหลัง · ถ้ารายที่สองมาแล้วรูปนี้ไม่พอ ทางแก้คือเพิ่ม field ในชั้นนอกซึ่ง option B ออกแบบให้ทำได้แบบ additive อยู่แล้ว

**Authority:** Monthop Champaruang — Platform Owner / Architecture Authority of `agent-platform`

### ไม่ bump major — อยู่ใน `v1` เดิม

| เกณฑ์ breaking ของ [ADR-0006](0006-contract-versioning.md) | การเปลี่ยนนี้ |
| --- | --- |
| ลบ field · เปลี่ยนชื่อ field · เปลี่ยน type | ❌ ไม่มี field เดิมถูกแตะ |
| เพิ่ม required field ใหม่ · optional → required | ❌ `required` ยัง 8 ตัวเท่าเดิม |
| ลบค่าออกจาก enum · เปลี่ยนความหมายของค่าเดิม | ❌ ไม่มี enum ใน contract นี้ |
| เปลี่ยน default ที่ทำให้พฤติกรรมเดิมเปลี่ยน | ❌ ไม่มี default · ไม่มี `conditions` = ไม่มีเงื่อนไข ซึ่งตรงกับพฤติกรรมเดิมทุกประการ |
| เข้มขึ้นใน validation | ⚠️ `additionalProperties: false` อยู่ที่ **ตัว Condition เท่านั้น** ซึ่งเป็น object ที่เพิ่งเกิด — ตัว grant ยังเปิดเหมือนเดิม payload เดิมจึงไม่มีใบไหน invalid |

payload ที่ valid กับ `v1.0.0` **ยัง valid ทุกใบ** → `v1.1.0` ใน `CHANGELOG.md` โดยไม่สร้าง `v2/`

`consent/v1` ไม่มี `derived_from` — ไม่มี `semantics_version` ให้ขยับ และไม่ต้องรอ RFC ที่ repo ไหน

## Consequences

* `contracts/consent/v1/consent.schema.yaml` เพิ่ม `$defs.Condition` + `conditions` · `consent_rules` และ `platform_rules` ยาวขึ้น · `CHANGELOG.md` → `v1.1.0`
* `care-agent-platform` migrate `{kind, <domain keys>}` → `{kind, params: {...}}` แล้ว bump pin — ตอบที่ [#25](https://github.com/monthop-gmail/agent-platform/issues/25) ให้รู้รูปสุดท้ายก่อน payload รูปเก่าสะสม
* **`consent/v1` เลิกเป็นสัญญาที่ตอบตัวเองได้** สำหรับใบที่มีเงื่อนไข — บันทึกไว้ในตัว schema เพราะเป็นสิ่งที่คนอ่านผ่าน ๆ จะพลาด
* **drift check ตรวจข้อนี้ไม่ได้เลย** — ตรวจได้แค่ว่า schema ยัง valid และ `kind` ไม่ถูกปิดเป็น enum · กฎ "ตรวจทุกครั้งที่ใช้" กับ "ไม่รู้จัก = ไม่อนุญาต" พิสูจน์ได้จาก **เทสของ consumer ที่รัน payload จริง** เท่านั้น (S16/S17) — ตรงกับที่ [ADR-0011](0011-conformance-automation.md) จำกัดขอบเขต `conformance/` ไว้ และตรงกับที่ทุกช่องโหว่ก่อนหน้านี้ถูกเจอ
* `policy/v1` **ไม่แตะในรอบนี้** — `Decision` เพิ่ม optional `consent_id` ยังค้างจาก `v1.0.0` อยู่แล้ว ([CHANGELOG](../contracts/consent/v1/CHANGELOG.md) "ยังไม่ทำในรอบนี้") · รวมสองเรื่องเข้าด้วยกันจะทำให้ `consent/v1` ยืนเองไม่ได้อีก
* ช่องว่างเรื่อง audit ย้อนหลัง (event ต้องบันทึกว่าเงื่อนไขผ่านแล้ว) **ค้างไว้โดยตั้งใจ** — ผูกกับ [#23](https://github.com/monthop-gmail/agent-platform/issues/23) ที่จะเคาะเรื่อง trail ที่ตรวจสอบได้ ไม่ควรตัดสินสองเรื่องนี้แยกกัน
