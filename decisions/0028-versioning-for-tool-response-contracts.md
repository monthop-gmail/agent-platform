# ADR-0028: contract ที่ส่งผ่าน tool response — กฎ versioning สำหรับช่องทางที่ประกาศไปไม่ถึงผู้รับ

**Status:** **Accepted** (2026-09-07)
**อัปเดต:** 2026-09-07 — บันทึกนาฬิกาเรือนที่สาม (ข้อเท็จจริงที่ผู้ขอวัดได้หลัง deploy) · ปิดข้อค้างเรื่องคีย์ที่ถูกลบไปแล้ว · กติกาถูก implement และยืนยันจากฝั่งผู้ใช้แล้ว
**Date:** 2026-09-07
**Depends on:** [ADR-0006](0006-contract-versioning.md) · [ADR-0011](0011-conformance-automation.md) · [ADR-0027](0027-toolid-transformation-must-be-deterministic.md)
**Blocking:** `contracts/mcp/v1` (ยังไม่แตะ) · คำขอจาก [`ai-collaboration-mcp`](https://github.com/monthop-gmail/ai-collaboration-mcp)

## Context

7 ก.ย. 2026 `ai-collaboration-mcp` เปลี่ยนรูปผลลัพธ์ของ `get_workspace_context` จาก

```text
waiting_for_you { handoffs, tasks }        →  waiting_for_you { unaccepted, in_progress }
```

**คีย์เดิมถูกลบทิ้ง** ไม่มีเลขเวอร์ชัน ไม่มีช่วง deprecation และประกาศด้วยประโยคว่า *"ใครที่เขียนไว้ว่าอ่านสองคีย์นั้นต้องแก้"* — ตรงตามนิยาม breaking ใน [ADR-0006](0006-contract-versioning.md) ทุกข้อ

`agent-platform` ไม่พังเพราะไม่ได้เขียนโค้ดอ่านคีย์นั้น แต่ทักไปว่าเป็น breaking change ที่ ship โดยไม่มีที่ให้ประกาศเวอร์ชันเลยแม้แต่ช่องเดียว · ผู้ดูแลรับว่าเป็นความผิดฝั่งตัวเองชัด ๆ และ **ขอให้ `agent-platform` เป็นคนร่างกติกา** ซึ่งตรงกับขอบเขตที่ [ADR-0006 A2](0006-contract-versioning.md) วางไว้ว่า platform เป็นเจ้าของ *รูปร่างบน wire* และกฎ versioning

### ข้อจำกัดสามข้อที่เขาวัดมาเอง — และมันตัดทางเลือกทั้งตระกูลออก

| # | ข้อเท็จจริง | ผลที่ตามมา |
| --- | --- | --- |
| 1 | server เป็น **stateless** ไม่มี session ค้างระหว่างคำขอ | ส่ง `notifications/tools/list_changed` ของ MCP **ไม่ได้เลย** — กติกาใดที่ตั้งอยู่บน *"server ประกาศแล้ว client จะรู้"* ใช้ที่นี่ไม่ได้ทั้งชุด |
| 2 | ผลลัพธ์ของ tool **สร้างสดทุกครั้ง** ส่วน tool list / `inputSchema` / `description` **ค้างอยู่ที่ client** จนกว่าจะเชื่อมต่อใหม่ | มีช่วงเวลาที่ client ถือคำอธิบายเก่าแต่ได้ข้อมูลใหม่ไปแล้ว · ยาวแค่ไหนขึ้นกับว่าใครเปิดแชตใหม่เมื่อไหร่ ซึ่งฝั่ง server **มองไม่เห็นและเร่งไม่ได้** · ⚠️ ท่อน *"ผลลัพธ์เปลี่ยนพร้อมกันหมดทุก client ทันทีที่ deploy จบ"* ที่มากับข้อนี้เดิม **ผู้ให้ข้อมูลถอนแล้ว** ดูนาฬิกาเรือนที่สามข้างล่าง |
| 3 | `serverInfo.version` เป็น `0.1.0` **hardcode มาตั้งแต่วันแรก** ไม่เคยขยับทั้งที่ contract เปลี่ยนมาสามรอบ | ช่องที่มีอยู่แล้วไม่ได้ถูกใช้ · และมันอยู่ระดับ protocol ซึ่ง **โมเดลผู้เรียกไม่เห็นค่านั้นในบริบทของตัวเอง** คนที่เห็นคือ client ที่ห่ออยู่ |

## นาฬิกาสามเรือน — ข้อสังเกตที่เปลี่ยนรูปคำถาม

สิ่งที่ประกอบกันเป็น contract ของ MCP tool ถูก cache คนละแบบ:

```text
ผลลัพธ์ของ tool        สร้างสด → เปลี่ยนเมื่อ isolate ที่รับคำขอนั้นเป็นตัวใหม่
description/schema     ค้างที่ client → เปลี่ยนเมื่อ client เชื่อมต่อใหม่ ซึ่งไม่มีใครรู้ว่าเมื่อไหร่
ช่วง rollout           isolate เก่ากับใหม่ตอบพร้อมกัน → สองรูปมีชีวิตพร้อมกันชั่วขณะ
```

**เรือนที่สามเพิ่มเข้ามาหลังเคาะ และเป็นการวัดของฝั่งผู้ขอเอง ไม่ใช่ข้อสันนิษฐานของเรา** — เดิม `seq 13` ระบุว่าผลลัพธ์ *"เปลี่ยนพร้อมกันหมดทุก client ตั้งแต่วินาทีที่ deploy จบ"* และ ADR ฉบับแรกอ้างประโยคนั้น · ตอน deploy กติกานี้จริง เขายิง `get_workspace_context` ทันทีหลัง deploy จบแล้ว **ยังไม่มีฟิลด์ `contract`** ยิงซ้ำอีกไม่กี่วินาทีถัดมาจึงได้ครบ แล้วถอนประโยคเดิมของตัวเองใน `seq 15`

**ข้อนี้ไม่ได้ลดน้ำหนักของคำตอบ แต่เพิ่ม** — กติกาที่พึ่งการประกาศต้องถูกทั้งสามเรือนจึงจะรอด ส่วนกฎห้ามลบไม่ต้องถูกสักเรือน เพราะทุกรูปที่มีชีวิตอยู่ในช่วงนั้นมีคีย์เก่าครบเหมือนกัน

**ทุก breaking change จึงมีช่วงที่ผู้เรียกถือคำอธิบายเก่าแต่ได้ข้อมูลใหม่โดยไม่มีสัญญาณอะไรบอก** — ไม่ใช่ข้อบกพร่องของ server ตัวนี้ แต่เป็นคุณสมบัติของ MCP เอง

คำถามจึงไม่ใช่ *"จะประกาศเวอร์ชันยังไง"* แต่เป็น **"จะออกแบบยังไงให้ไม่ต้องพึ่งการประกาศ"**

## ทำไม ADR-0006 ตอบข้อนี้ไม่ครบ ทั้งที่มีนิยาม breaking อยู่แล้ว

**นิยาม breaking ย้ายมาใช้ได้เกือบทั้งดุ้น** สิ่งที่ย้ายมาไม่ได้คือ **กลไกบังคับ** ซึ่ง ADR-0006 พึ่งอยู่สี่อย่าง และไม่มีสักอย่างที่มีอยู่จริงในช่องทางนี้:

| กลไกใน ADR-0006 | ทำไมใช้กับ tool response ไม่ได้ |
| --- | --- |
| consumer **pin version** ตรง ๆ ที่ path `contracts/<name>/v1/` | ผู้เรียกไม่มีอะไรให้ pin — ได้รูปอะไรมาก็ต้องรับรูปนั้น |
| **แจ้ง consumer ที่ pin ไว้ทุกตัว** | stateless · ส่งประกาศไปหาใครไม่ได้ (ข้อจำกัดข้อ 1) |
| ตรวจจาก [`architecture/consumers.md`](../architecture/consumers.md) | ผู้เรียกเป็น **โมเดล** ไม่ได้ขึ้นทะเบียนไว้ที่ไหน และไม่มีทางรู้ว่าค่ายไหนถือ schema เวอร์ชันไหน |
| **90 วันหลัง `vN+1` พร้อมใช้** | นับจากอะไรไม่ได้ เพราะจุดที่ client ย้ายจริงคือตอน reconnect ซึ่งมองไม่เห็น |

### และมีช่องว่างเชิงทิศทางที่ ADR-0006 ไม่ได้เขียนไว้

ลิสต์ใน ADR-0006 เขียนจากมุมของ **เอกสาร/คำขอ** ไม่ใช่มุมของ **คำตอบ** — บางข้อจึงกลับทิศ:

| การเปลี่ยน | ในคำขอ (ADR-0006 เดิม) | ในคำตอบ |
| --- | --- | --- |
| เพิ่ม field ที่มีเสมอ | **breaking** (บังคับผู้ส่งให้ส่งเพิ่ม) | **ไม่ breaking** — ผู้ผลิตสัญญามากขึ้น ผู้รับที่ไม่สนใจก็ไม่เดือดร้อน |
| ลบ/เปลี่ยนชื่อ key | breaking | **breaking** — และเป็นข้อที่เกิดจริงในรอบนี้ |
| เพิ่มค่าใน enum | ไม่ breaking (ถ้าเผื่อไว้แล้ว) | **breaking กว่า** — ผู้รับเจอค่าที่ไม่รู้จักโดยไม่มีที่ให้ fallback ถ้ากติกาไม่ได้บังคับไว้ล่วงหน้า |

## Options

### A. ไม่เขียนอะไรเพิ่ม — ใช้ ADR-0006 ตามเดิม

* ✅ ไม่มีกติกาซ้อนกันสองชุด
* ❌ กลไกบังคับสี่อย่างของ ADR-0006 **ไม่มีสักอย่างที่ทำงานได้** ในช่องทางนี้ — เท่ากับเขียนกฎแล้วไม่มีอะไรมารองรับ ซึ่งเป็นแผลที่ repo นี้ปิดมาแล้วหกครั้ง
* ❌ ช่วง deprecation 90 วันนับจากอะไรไม่ได้เลย

### B. ใส่เลขเวอร์ชันในผลลัพธ์อย่างเดียว

* ✅ machine-readable · ทำได้ทันที ไม่ต้องพึ่ง notification
* ✅ อย่างน้อย audit ย้อนหลังบอกได้ว่าข้อมูลชุดนั้นมาจาก contract รุ่นไหน
* ❌ **client ที่ถือ description เก่าไม่มีอะไรมาเทียบ** — รู้ว่าเลขคือ 4 แต่ไม่รู้ว่าตัวเองถือ 3 อยู่ · เลขที่ไม่มีคู่เทียบไม่ได้เตือนใคร
* ❌ ไม่ได้แก้ปัญหาคีย์ที่หายไปแล้ว — โค้ดที่อ่านคีย์เก่ายังพังเหมือนเดิม

### C. เลขสองที่ที่ถูก cache คนละแบบ แล้วให้ผู้เรียกเทียบเอง — *ข้อเสนอของ `ai-collaboration-mcp`*

ใส่เลขไว้ใน `description` ของ tool (ค้างที่ client) และในผลลัพธ์ของ `get_workspace_context` (สร้างสด) → ถ้าสองเลขไม่ตรง แปลว่ากำลังถือ schema เก่า ต้อง reconnect

* ✅ **ตรวจได้โดยไม่ต้องเชื่อคำกล่าวอ้างของใคร** ซึ่งเป็นหลักเดียวกับที่ repo นี้ใช้มาตลอด
* ✅ ไม่พึ่ง notification ที่ส่งไม่ได้อยู่แล้ว — ใช้ความต่างของนาฬิกาสองเรือนให้เป็นประโยชน์แทนที่จะเป็นปัญหา
* ❌ ผู้ตรวจคือ **โมเดล** ไม่ใช่โค้ด · `description` เป็น prose ที่เขียนให้โมเดลอ่าน เอาไปเทียบด้วยเครื่องไม่ได้
* ⚠️ ข้อเสียข้างบนจะจริงก็ต่อเมื่อปล่อยให้เป็น prose — **ถ้าบังคับให้สิ่งที่ถูกเทียบเป็นจำนวนเต็มในตำแหน่งตายตัว** (เช่นบรรทัดแรกของ description เป็น `contract: 4` เท่านั้น) การเทียบจะเหลือแค่ *เลขสองตัวนี้ตรงกันไหม* ซึ่งโมเดลตอบได้แม่น
* ❌ ต่อให้เตือนได้ ก็ยังเป็นการเตือน **หลังจากที่ของพังไปแล้ว** — ไม่ได้ทำให้ client เก่าทำงานต่อได้

### D. C + **ห้ามลบคีย์เก่าจนกว่าจะขึ้น major** (additive-only ภายใน major) ⭐

* ✅ **ทำให้การเทียบเลขกลายเป็น "ดีถ้ามี" ไม่ใช่ "ต้องมี"** — client ที่ถือของเก่ายังหาคีย์ของมันเจอ จึงไม่พังตั้งแต่แรก · ข้อจำกัดข้อ 1 (ส่งประกาศไม่ได้) **หมดความสำคัญทันที** เพราะไม่มีอะไรต้องประกาศให้ทัน
* ✅ **ต้นทุนเกือบศูนย์** — ผลลัพธ์สร้างสดทุกครั้ง การคงคีย์เก่าไว้คู่กันไม่ต้อง migrate ข้อมูล ไม่ต้องแตะ schema ของฐานข้อมูล ต่างจากไฟล์ contract ที่การมีสองรูปแปลว่ามีสองไฟล์
* ✅ **เป็นกฎเดียวกับ ADR-0006 อยู่แล้ว** — field ที่ `deprecated: true` อยู่ต่อจนกว่าจะขึ้น major ([`contracts/README.md`](../contracts/README.md)) · ไม่ได้สร้างกติกาใหม่ แค่ย้ายกฎที่มีอยู่มาใช้กับช่องทางที่มันยังไม่เคยครอบ
* ✅ ทำให้ *"ห้ามพึ่งพาว่า consumer จะอ่าน field ใหม่ได้ทันที"* ใน ADR-0006 กลายเป็นข้อบังคับที่มีผลจริง แทนที่จะเป็นคำแนะนำ
* ❌ ผลลัพธ์อ้วนขึ้น และมี **สองชื่อสำหรับของเดียวกันชั่วคราว** ซึ่ง repo นี้ห้ามไว้ทุกที่ (`expires_at: null` · `conditions: []` · `Request.subject`)
* ⚠️ ข้อเสียข้างบนกันได้ด้วยเงื่อนไขเดียวกับที่ ADR-0006 ใช้ — **ต้องมีทะเบียนคีย์ที่รอลบ พร้อมระบุว่าลบเมื่อขึ้น major ตัวไหน** ไม่ใช่ปล่อยให้เป็นชื่อที่สองถาวร

### E. breaking = ออก tool ชื่อใหม่ (`get_workspace_context_v2`)

* ✅ client เก่าไม่พังเลยแม้แต่นิดเดียว · แยกขาดชัดเจนที่สุด
* ❌ **tool list บวมทุกครั้งที่ contract เปลี่ยน** และ tool list คือของที่ค้างอยู่ที่ client — ยิ่งบวมยิ่งกินบริบทของโมเดลทุกตัวที่ต่ออยู่
* ❌ client เก่าจะเรียกตัวเก่าต่อไป **ตลอดกาล** โดยไม่มีใครรู้ว่ายังมีใครเรียกอยู่ — ไม่มีวันปิดตัวเก่าได้อย่างมั่นใจ
* ❌ ชื่อ tool กลายเป็นที่เก็บเวอร์ชัน ซึ่งเป็นสิ่งที่ [ADR-0006](0006-contract-versioning.md) ปฏิเสธไปแล้วตอนเลือกไม่ใส่เวอร์ชันในชื่อ field

## Decision

**D** — เลขสองที่ที่ถูก cache คนละแบบ **บวกกับ** ห้ามลบคีย์เก่าจนกว่าจะขึ้น major

**Reason:** ข้อจำกัดที่เขาวัดมาบอกว่าการประกาศไปไม่ถึงผู้รับ และ *"ยาวแค่ไหนไม่มีใครรู้"* · กติกาใดที่ต้องให้ผู้รับรู้ตัวก่อนจึงจะรอด ย่อมล้มเหลวเงียบในระบบแบบนี้ — ทางที่เหลือคือ **ทำให้ผู้รับที่ไม่รู้ตัวเลยก็ยังไม่พัง** ซึ่งได้จากการห้ามลบ ไม่ใช่จากการประกาศ · เลขสองที่ (C) ยังควรมี แต่ฐานะของมันเปลี่ยนจาก *กลไกกันพัง* เป็น *เครื่องมือวินิจฉัย* ซึ่งเป็นฐานะที่มันทำได้จริง

**Authority:** Monthop Champaruang — Platform Owner / Architecture Authority of `agent-platform`

### กฎที่ตีพิมพ์

```text
1. ภายใน major เดียวกัน ผลลัพธ์ของ tool เพิ่มคีย์ได้ ห้ามลบ ห้ามเปลี่ยนชื่อ ห้ามเปลี่ยนความหมายของคีย์เดิม
2. คีย์ที่ถูกแทนที่แล้วต้องอยู่ต่อคู่กับคีย์ใหม่ พร้อมขึ้นทะเบียนว่าจะลบเมื่อขึ้น major ตัวไหน
3. เลข contract เป็นจำนวนเต็ม ปรากฏสองที่ที่ถูก cache คนละแบบ
   — บรรทัดแรกของ description ของ tool (ค้างที่ client)
   — คีย์ระดับบนสุดของผลลัพธ์ที่สร้างสด
   เลขไม่ตรง = ผู้เรียกกำลังถือ schema เก่า ต้องเชื่อมต่อใหม่
4. เพิ่มค่าใน enum ของ **คำตอบ** ถือว่า breaking เว้นแต่กติกาได้บังคับ fallback ไว้ล่วงหน้าแล้ว
5. ช่วง deprecation ของช่องทางนี้ **ไม่มีหน่วยเป็นเวลา** — ผูกกับ major ไม่ใช่กับวัน
   เพราะจุดที่ผู้รับย้ายจริงคือตอน reconnect ซึ่งฝั่งผู้ส่งมองไม่เห็น
```

**ข้อ 5 คือข้อที่ต่างจาก ADR-0006 มากที่สุด และเป็นคำถามที่ผู้ขอบอกเองว่ายังไม่มีคำตอบ** — คำตอบคือคำถามตั้งผิด นาฬิกาที่ใช้นับ 90 วันไม่มีอยู่จริงในช่องทางนี้

### ไม่แตะ contract ใดเลย

ADR นี้ **ขยายกฎของ [ADR-0006](0006-contract-versioning.md) ไม่ใช่สร้าง contract ใหม่** — ตามเกณฑ์ข้อ 1 ใน [`contracts/README.md`](../contracts/README.md) ที่ว่า *"มี contract ที่มีอยู่แล้วตอบคำถามนี้ได้หรือไม่ — ถ้ามี ให้ขยายตัวนั้น"* · และเกณฑ์ข้อ 2 (consumer อย่างน้อย 2 ราย) ยังไม่ครบอยู่ดี เพราะตอนนี้มี MCP server ที่ขอเรื่องนี้รายเดียว

**เลขเวอร์ชันอยู่ในผลลัพธ์ของ server ซึ่งเป็น schema ของเขา ไม่ใช่ของเรา** — `mcp/v1` เป็นทะเบียนที่เราบันทึก *ว่ามี server ตัวนี้อยู่* ไม่ใช่ envelope ของคำตอบ · การเพิ่ม field ลง `mcp/v1` ตอนนี้คือเดารูปให้งานที่ยังไม่มีใครทำ ซึ่งเป็นเหตุผลเดียวกับ [ADR-0025](0025-provider-switch-and-what-identity-covers.md) และ [ADR-0027](0027-toolid-transformation-must-be-deterministic.md) ที่เขียนกฎก่อนสร้าง field

## Consequences

* **ช่วง deprecation แบบ 90 วันใน ADR-0006 ไม่มีผลกับ tool response** — ต้องเขียนกำกับไว้ในตัว ADR-0006 ด้วย ไม่งั้นจะมีสองกฎที่อ่านแล้วขัดกัน
* **drift check ตรวจข้อนี้ไม่ได้** — [ADR-0011](0011-conformance-automation.md) ห้าม `conformance/` เรียก host อื่นนอกจาก `raw.githubusercontent.com` · พิสูจน์ได้จากเทสฝั่ง server เท่านั้น เหมือนกรณี [ADR-0027](0027-toolid-transformation-must-be-deterministic.md)
* **ทะเบียนคีย์ที่รอลบต้องอยู่ฝั่ง server** ไม่ใช่ที่ [`contracts/README.md`](../contracts/README.md) ของเรา เพราะไม่ใช่ contract ที่เราถือ — เราถือแค่กฎ
* **ปิดแล้ว — คีย์ที่ถูกลบเมื่อ 7 ก.ย. ไม่คืน · จุดเริ่มของกฎคือ `contract 2`** · เจ้าของ server เคาะไม่คืน และเหตุผลที่ตัดสินคือข้อที่ **ฝั่งเรามองข้าม**: `waiting_for_you.total` เป็นคีย์ที่ *ยังอยู่แต่ความหมายเปลี่ยน* (เดิมนับซ้ำได้ `2` ตอนนี้ไม่นับซ้ำได้ `1`) ซึ่งกฎข้อ 1 ท่อน *ห้ามเปลี่ยนความหมาย* ห้ามไว้เหมือนกัน — **การคืนแค่ `handoffs`/`tasks` จึงไม่ได้ทำให้ถูกกฎ ต้องคืน `total` แบบเดิมด้วย ซึ่งเท่ากับคืนบั๊กที่ทั้งสองทีมเห็นพ้องกันว่าผิด** · ตอนเราเสนอให้คืน เรานับแต่คีย์ที่หายไป ไม่ได้นับคีย์ที่ยังอยู่แต่ความหมายเปลี่ยน ทั้งที่กฎที่เราเขียนเองครอบทั้งสอง · ข้อยกเว้นครั้งเดียวนี้บันทึกไว้ที่ README และ NOTES ของ server แล้ว **ตั้งแต่ `2` เป็นต้นไปกฎมีผลเต็ม**
* **กติกาถูก implement และยืนยันจากฝั่งผู้ใช้แล้ว** — `agent-platform` ยิงเทียบเองในฐานะ client ที่ไม่ได้อยู่ในการ deploy: `description` ที่ client ถืออยู่ขึ้นต้นว่า `contract 2` และ `get_workspace_context` ที่ยิงสดคืน `contract: 2` · **ตรงกัน** · ฝั่ง server ทำเป็น wrapper ของ `registerTool` ไม่ใช่เขียนเลขในข้อความของแต่ละ tool — เหตุผลเดียวกับ [ADR-0027](0027-toolid-transformation-must-be-deterministic.md) คือกฎที่ต้องอาศัยความจำของคนเขียนจะถูกละเมิดทันทีที่คนเปลี่ยน
* **ยังไม่ปิด:** ที่ทางของเลข contract ใน `mcp/v1` — รอ consumer รายแรกที่ pin ตามหลักเดียวกับ mapping record ใน [ADR-0027](0027-toolid-transformation-must-be-deterministic.md)
* ยังไม่มีใครตอบได้ว่า **ค่ายไหนถือ schema เวอร์ชันไหนอยู่** — ภายใต้ D ข้อนี้เลิกเป็นเรื่องคอขาดบาดตาย เพราะคนที่ถือของเก่าก็ยังทำงานได้ แต่ยังเป็นข้อจำกัดที่ต้องบันทึก
