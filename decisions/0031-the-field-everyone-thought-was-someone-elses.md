# ADR-0031: ฟิลด์ที่ทุกคนคิดว่าเป็นของคนอื่น — `Principal.display_name` อยู่ใน audit ทุกใบที่เคยเขียน

**Status:** **Accepted** (2026-09-11)
**Date:** 2026-09-11
**Depends on:** [ADR-0030](0030-the-field-nobody-named.md) · [ADR-0018](0018-policy-result-single-source.md) · [ADR-0007](0007-multi-tenancy.md)
**Blocking:** `contracts/identity/v1` → `v1.2.0`

## Context

`agent-platform` ร่าง invariant สำหรับ RFC ที่จะยื่นที่ `devfactory-core` แล้วส่งให้ `care-agent-platform` ลองกับของจริงก่อนยื่น · เขา **ไม่ได้อ่านร่างแล้วตอบ** แต่เขียนตัวไล่ทุก leaf ของ audit event จริง **112 ใบ** แล้วถามว่า leaf ไหนไม่ใช่ตัวชี้

```text
actor.display_name                   112/112 ใบ   ← ทุกใบที่ระบบเคยเขียน
evidence.recorded_by.display_name      9 ใบ
metadata.policy_reason                26 ใบ
transition.reason                     37 ใบ
```

สองอันแรก **ไม่มีใครเคยเห็นมาก่อน** — ชื่อคนจริง อยู่ในทุก event ตั้งแต่ใบแรก ในที่ที่ลบไม่ได้เพราะ append-only และสิทธิ์การอ่านไม่ผูกกับ consent แบบเดียวกับตารางของโดเมน

### ทำไมถึงไม่มีใครเห็น — และทำไมมันไม่ใช่แผลเดียวกับ ADR-0030

[ADR-0030](0030-the-field-nobody-named.md) บันทึกไว้ว่า `error/v1.details` รอดมาสามสัปดาห์เพราะ **ไม่มีใครเอ่ยชื่อมัน** · รอบนี้เป็นคนละเหตุผล และผู้รายงานชี้เอง:

> ต่างกันแค่รอบนี้ของที่รอดมา **ไม่ได้รอดเพราะไม่มีใครเอ่ยชื่อมัน แต่รอดเพราะทุกคนคิดว่ามันเป็นของแพลตฟอร์ม ไม่ใช่ของตัวเอง**
>
> มันไม่ใช่ฟิลด์ที่โดเมนใส่ **มันเป็นฟิลด์ของสัญญาเอง** ตอนผมไล่ปิด `metadata` ทั้งใบเมื่อวาน ผมดูแต่ของที่เราเขียนเองแล้วเดินผ่าน `actor` ไป ทั้งที่มันติดมาทุกใบ

รวมเป็นสามรูปของแผลเดียวกันที่พบภายในสองวัน:

```text
ชื่อที่กว้างเกิน          → คนใส่ของผิดเข้าไปโดยไม่รู้ตัว          (เคส reason ของ care)
ฟิลด์ที่ไม่มีใครเอ่ยชื่อ    → ไม่มีใครไปดูว่ามีอะไรอยู่ในนั้น        (ADR-0030 · error/v1.details)
ฟิลด์ของสัญญาเอง         → ทุกคนคิดว่าเป็นของอีกฝ่าย ไม่มีใครดู   (ใบนี้ · identity/v1.display_name)
```

**สามรูปนี้ไม่มีอะไรใน JSON Schema ตรวจได้เลยสักรูป**

### สถานะของฟิลด์ในสัญญาวันนี้

```yaml
  Principal:
    required: [type, id]        # display_name ไม่อยู่ใน required อยู่แล้ว
    properties:
      display_name:
        type: string            # ← ไม่มีคำอธิบายเลยสักบรรทัด
```

**การตัด `display_name` ออกจึง conform เต็มที่อยู่แล้วในวันนี้** ไม่ต้องรอสัญญาเวอร์ชันใหม่ — `care-agent-platform` ตัดที่จุด emit ที่เดียว รวม `on_behalf_of` ที่ซ้อนกันและ `evidence.recorded_by` ซึ่งเป็น `Principal` ตัวเดียวกัน แล้ว merge ไปแล้ว (`care-agent-platform#23`) พร้อม ratchet ใน `payload_check` ที่ทำให้ CI แดงถ้ามี leaf ที่ไม่ใช่ตัวชี้และไม่อยู่ในรายการที่ประกาศไว้

## Options

### A. ไม่ทำอะไร — ฟิลด์เป็น optional อยู่แล้ว ใครไม่อยากใส่ก็ไม่ใส่

* ✅ ไม่แตะสัญญา
* ❌ **ผู้ผลิตที่ทำตามสามัญสำนึกจะใส่** — ฟิลด์ชื่อ `display_name` อ่านตรง ๆ แปลว่าให้ใส่ชื่อ · ผู้รายงานเดาว่า consumer ทุกรายทำเหมือนกัน และไม่มีอะไรบอกเขาว่าราคาคืออะไร
* ❌ หลักฐานคือ **112/112 ใบ** ไม่ใช่ความเสี่ยงเชิงทฤษฎี

### B. ลบ `display_name` ออกจาก `Principal`

* ✅ ปิดสนิท ไม่มีทางใส่ผิด
* ❌ **breaking** ตาม [ADR-0006](0006-contract-versioning.md) — ลบ field คือขึ้น major
* ❌ ฟิลด์นี้มีประโยชน์จริงในบริบทที่อายุสั้น เช่น request context ที่ไม่ได้ถูกบันทึกถาวร · การลบทิ้งคือการแก้ปัญหาของ audit ด้วยการทำลายของที่ใช้ได้ในที่อื่น

### C. บังคับที่ `event/v1` แทน — ห้ามฝัง `Principal` ที่มี `display_name` ลง audit

* ✅ ตรงจุดที่ปัญหาเกิดจริง
* ❌ `event/v1` **derive semantics จาก `devfactory-core`** — เขียนกฎเองไม่ได้ ต้องมี RFC ที่ต้นทาง
* ❌ และปัญหาไม่ได้อยู่แค่ `event/v1` — `Principal` ถูกฝังในสัญญาอื่นด้วย การไล่ปิดทีละที่คือการไล่ตามอาการ

### D. เขียนคำกำกับที่ตัวฟิลด์ใน `identity/v1` ⭐

* ✅ **ปิดที่ต้นทางของฟิลด์** — ใครก็ตามที่เอา `Principal` ไปใช้ที่ไหนจะเห็นคำเตือนเดียวกัน โดยไม่ต้องไล่แก้ทุกสัญญาที่ฝังมันไว้
* ✅ `identity/v1` **เป็นของ `agent-platform` เต็มใบ ไม่ derive จากใคร** — แก้ได้เองวันนี้ ไม่ต้องรอ RFC
* ✅ ไม่ breaking — เพิ่มคำอธิบาย ไม่แตะ `type` ไม่แตะ `required`
* ✅ บอกทางออกที่ใช้ได้ทันทีไว้ในตัวฟิลด์ ว่าตัดออกได้เลยเพราะเป็น optional มาตั้งแต่ `v1.0.0`
* ❌ **เป็นคำเตือน ไม่ใช่การบังคับ** — validator กลางยังตรวจไม่ได้ว่าใครใส่ชื่อลงไป

## Decision

**D** — เขียนคำกำกับที่ `Principal.display_name` ใน `identity/v1` พร้อมบอกทางออกที่ใช้ได้ทันที

**Reason:** ฟิลด์นี้รั่วเข้า audit ทุกใบไม่ใช่เพราะใครประมาท แต่เพราะ **ไม่มีอะไรในสัญญาบอกว่าการใส่ชื่อลงไปมีราคาอะไร** และชื่อฟิลด์เองก็ชวนให้ใส่ · การปิดที่ `identity/v1` ทำให้คำเตือนเดินทางไปกับ `Principal` ทุกที่ที่มันถูกฝัง แทนที่จะไล่ปิดทีละสัญญาซึ่งเป็นการไล่ตามอาการ · ปฏิเสธ B เพราะ breaking และทำลายของที่ใช้ได้จริงในบริบทที่อายุสั้น · ปฏิเสธ C เพราะ `event/v1` ไม่ใช่ของเราที่จะเขียนกฎ และปัญหาไม่ได้อยู่ที่ `event/v1` ที่เดียว

**Authority:** Monthop Champaruang — Platform Owner / Architecture Authority of `agent-platform`

### `identity/v1` `v1.1.0` → `v1.2.0` — ไม่ breaking

เพิ่มคำอธิบาย · ไม่แตะ `type` ไม่แตะ `required` · `display_name` เป็น optional มาตั้งแต่ `v1.0.0` แปลว่า **ผู้ผลิตตัดออกได้วันนี้โดยยัง conform** ไม่ต้องรอสัญญาเวอร์ชันใหม่

## Consequences

* **consumer ที่ pin `identity/v1` ทุกรายควรไล่ leaf ของ audit ตัวเอง** — `care-agent-platform` · `devfactory-core` · `ecosystem-intelligence` · `agent-builder-dsh-poc` · เครื่องมือที่ใช้ตรวจใช้เวลาเขียนไม่ถึงชั่วโมงตามที่ผู้รายงานระบุ และมันเจอของที่ validator เดิมทุกตัวมองไม่เห็น เพราะ **validator เดิมถามว่าใบนี้ถูกรูปไหม ไม่มีตัวไหนถามว่าในใบนี้มีอะไรอยู่**
* **ใบที่เขียนไปแล้วแก้ไม่ได้** — append-only เป็น guarantee ของ `event/v1` เอง · สิ่งที่ทำได้คือหยุดใบใหม่ ไม่ใช่แก้ใบเก่า · เกณฑ์ที่ใช้วัดจึงเป็น *ตั้งแต่วันไหนที่ไม่มีใบใหม่ละเมิดอีก* ไม่ใช่เปอร์เซ็นต์ที่ปิดได้
* **drift check ตรวจข้อนี้ไม่ได้** — [ADR-0011](0011-conformance-automation.md) ห้าม `conformance/` เรียก host อื่น · เหมือน [ADR-0030](0030-the-field-nobody-named.md)
* **บทเรียนที่ต่อจาก ADR-0030** — ครั้งหน้าที่ไล่ปิด PII ใน audit ให้ไล่จาก **leaf ของ payload จริง** ไม่ใช่จากรายการฟิลด์ที่ตัวเองเขียน · สองรายการนี้ไม่เท่ากัน และส่วนต่างคือฟิลด์ที่สัญญาใส่ให้เอง
* **ยังไม่ปิด:** `event/v1.transition.reason` และคำถามว่า `metadata` ถือคีย์ข้อความที่ประกาศไว้ได้หรือไม่ — อยู่ใน RFC ที่จะยื่นที่ `devfactory-core`
