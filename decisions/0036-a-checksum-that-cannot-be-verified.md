# ADR-0036: `artifact/v1.checksum` รับ `{}` และ `{value}` ได้ — และ "ไม่มีใคร pin" ไม่ได้แปลว่า "ไม่มีใครใช้"

**Status:** **Accepted** (2026-10-17)
**Date:** 2026-10-17
**Depends on:** [ADR-0006](0006-contract-versioning.md) นิยาม breaking · [ADR-0023](0023-frozen-bindings-and-identity.md) · [ADR-0025](0025-provider-switch-and-what-identity-covers.md) · [ADR-0032](0032-producer-ahead-of-contract.md) · [ADR-0035](0035-approval-bound-to-an-id-is-not-bound-to-what-runs.md)
**Blocking:** `contracts/artifact/v1` → `v1.1.0` (ครึ่งที่ไม่ breaking) · การบังคับทั้งหมดเป็นงานของ `artifact/v2` ที่ยังไม่เปิด

## Context

หนี้ใบนี้ประกาศไว้แล้วสองที่ ไม่ได้เพิ่งคิด — [ADR-0035](0035-approval-bound-to-an-id-is-not-bound-to-what-runs.md) Consequences และ `dis-514ae7a7` `seq 81` ข้อ 5ก · โผล่มาตอนทำ `payload_digest` เพราะ Option C ที่รับไป **ยืมรูป `{algorithm, value}` มาจากไฟล์นี้** แล้วพอเปิดไฟล์ไปลอกรูป ก็เห็นว่าตัวแบบเองไม่มีกฎ

```yaml
# contracts/artifact/v1/artifact.schema.yaml:31  (v1.0.0 · 2026-08-17 · ไม่เคยแก้)
  checksum:
    type: object
    properties:                  # ไม่มี required · ไม่มี additionalProperties · value ไม่มี pattern
      algorithm: { enum: [sha256, sha512] }
      value: { type: string }
```

### สามสภาพที่ต่างกันจริง ยุบเป็นสภาพเดียวในสายตา validator

```text
ไม่มี checksum เลย         valid    ไม่ได้คำนวณ / ไม่ได้อ้าง           ← สภาพเดียวที่ซื่อสัตย์
checksum: {}               valid    วัตถุที่ประกาศว่ามี checksum โดยไม่มี
checksum: {value: "abc"}   valid    แฮชที่ตรวจไม่ได้ เพราะไม่รู้อัลกอริทึม
checksum: {value: ""}      valid    ไม่มี minLength ด้วย
```

สองสภาพกลางคือรูปที่รีโปนี้ไล่ปิดมาทั้งปี — **ช่องที่มีค่าแต่ค่านั้นยืนยันอะไรไม่ได้ แรงกว่าช่องที่ไม่มี เพราะผู้อ่านเห็นว่ามีแล้วเชื่อว่าตรวจแล้ว**

### และข้อที่หนักกว่า — checksum ของ artifact ไม่มีตัวชี้ว่ามันคลุมอะไร

`checksum` ไม่ได้อยู่ใน `required` และ **`uri` ก็ไม่ได้อยู่** (`required: [artifact_id, tenant_id, type, created_at]`)

```text
{artifact_id, tenant_id, type, created_at, checksum: {algorithm: sha256, value: <64 hex>}}
→ valid · และเป็นแฮชของ "อะไร" ที่ไม่มีช่องไหนในใบบอกได้เลย
```

`uri` คือตัวชี้ไป storage ซึ่ง**เนื้อเปลี่ยนได้โดยที่ `artifact_id` ไม่เปลี่ยน** · `checksum` คือช่องเดียวที่จะจับข้อนั้นได้ แต่วันนี้มันไม่มีรูปพอจะจับ และไม่ประกาศว่าตัวเองคลุมอะไร — ตรงกับที่ [ADR-0023](0023-frozen-bindings-and-identity.md) เขียนไว้เองว่า

> *"checksum ที่คำนวณจาก manifest อย่างเดียว บอกได้แค่ว่า manifest เหมือนกัน ไม่ได้บอกว่าสิ่งที่รันเหมือนกัน — ถ้า identity ไม่ครอบ binding คำว่า reproducible จะไม่มีความหมาย"*

และ

> *"checksum ที่อ้างมากกว่าสิ่งที่มันครอบ คือ false ✅ ตระกูลเดียวกับที่ repo นี้ไล่ปิดมาตลอด"*

**เราเขียนกฎนั้นเมื่อ 20 ก.ย. แล้วปล่อยไฟล์ของเราเองละเมิดมันอยู่** — `payload_digest` ที่เพิ่งขึ้นเมื่อวันนี้บังคับ `covers` ด้วยเหตุผลนี้เป๊ะ ขณะที่ต้นแบบที่มันลอกมายังไม่มี

## 🔴 สาเหตุเชิงโครงสร้าง — ทะเบียนวัด *การประกาศ* ไม่ได้วัด *การเอื้อมถึง*

ผมรายงานกับเจ้าของงานก่อนร่างใบนี้ว่า *"ไม่มี consumer รายไหน pin `artifact/v1` เลย ศูนย์ราย — breaking ในทางทฤษฎีแต่ไม่มีใครตกเลยวันนี้"* · **ตัวเลขนั้นถูก แต่ตอบคำถามผิด** และข้อนี้เปลี่ยนคำแนะนำของใบนี้ทั้งใบ

ทะเบียนบันทึกไว้ตรง ๆ ว่าไม่มีใคร pin:

```text
architecture/consumers.md:86
| `tool` `mcp` `artifact` | *(ยังไม่มีใคร)* | — | ไม่มี v2 |
```

แต่ `artifact/v1` ถูกเอื้อมถึงผ่าน `$ref` ของสัญญาใบอื่น:

```text
contracts/execution/v1/execution.schema.yaml:146
  artifacts:
    type: array
    items:
      $ref: …/artifact/v1/artifact.schema.yaml

execution/v1 ถูก pin โดย   devfactory-core ✅ passing   ·   agent-builder-dsh-poc ✅ passing
```

**ผู้ผลิตที่ส่ง `execution/v1` พร้อม `artifacts[]` กำลังใช้ `artifact/v1` อยู่ โดยไม่เคย pin มัน** · การเข้มขึ้นที่ `checksum` จึงตกใส่สองรายนี้ได้จริง แม้ทะเบียนจะอ่านว่าศูนย์

> ทะเบียนตอบคำถามว่า *"ใครประกาศ pin"* · คำถามที่ต้องใช้ตัดสิน breaking คือ *"ใครส่ง payload ที่ validate กับไฟล์นี้"* — **สองคำถามนี้ไม่ใช่คำถามเดียวกัน และทะเบียนไม่เคยอ้างว่าตอบข้อหลัง**

เป็นรูปเดียวกับห้ารูปของ false pass ที่ `conformance/README.md` บันทึกไว้ — รูปที่หนึ่ง: **ตัววัดไม่ได้อยู่ตรงจุดที่ของพัง** · และรอบนี้ผมเป็นคนอ่านตัวเลขผิดเอง ไม่ใช่ตัวเลขผิด

### ข้อจำกัดของการตรวจรอบนี้

ตรวจได้ว่า **ใครอาจตก** · ตรวจไม่ได้ว่า **ใครตกจริง** — payload จริงของ `devfactory-core` และ `agent-builder-dsh-poc` อยู่ที่ runtime ของเขา ไม่ได้อยู่ในรีโปของเรา และ [ADR-0011](0011-conformance-automation.md) ห้าม `conformance/` เรียก host อื่น · **ต้องถามเจ้าของสองรีโปนั้น ช่องทางเดียวที่ทำได้คือ issue/PR comment**

## ของที่ ADR-0006 บังคับไว้แล้ว และปิดทางที่ง่ายที่สุดไปแล้ว

[ADR-0006](0006-contract-versioning.md) นิยาม breaking ไว้เป็นลิสต์ และ **เขียนข้อนี้ไว้ตรงตัว**

```text
เข้มขึ้นใน validation (เช่น ลด maxLength, เพิ่ม pattern)   = breaking → ขึ้น major ใหม่
เปลี่ยน field จาก optional → required                      = breaking → ขึ้น major ใหม่
```

ทั้งสามท่าที่จะปิดแผลนี้ — `required: [algorithm, value]` · `additionalProperties: false` · `pattern` ที่ `value` — **เข้านิยาม breaking ทั้งหมด** ทางที่บังคับได้จริงจึงคือ `artifact/v2` ไม่ใช่การขยับเลขหลังจุด

**ต่างจาก `payload_digest` ที่เพิ่งทำวันนี้อย่างไร** — `payload_digest` เป็นช่องใหม่ที่ไม่เคยอยู่ในเวอร์ชันที่เผยแพร่ไหนเลย · รูปหลวมของมันอยู่บน branch ไม่ถึงหนึ่งสัปดาห์และไม่เคยเป็น `v1.4.0` ที่ประกาศออกไป · การเข้มขึ้นกับช่องที่ยังไม่เคยเผยแพร่ไม่ใช่การเข้มขึ้นกับสัญญา — **ส่วน `checksum` เผยแพร่มาแล้วสองเดือน**

## Options

### A. ไม่ทำอะไร — บันทึกแผลไว้เฉย ๆ
* ✅ ไม่มีใครตก
* ❌ `{}` และ `{value}` ยังผ่าน และผู้อ่านยังเชื่อว่าตรวจแล้ว
* ❌ **เราถือกฎที่ตัวเองละเมิดอยู่** (ADR-0023) ซึ่งเป็นสภาพที่ ADR-0023 เองเรียกว่า *"การรับรองบั๊กนั้นไปด้วย"*

### B. เข้มขึ้นใน `v1` เลย — `required` + `additionalProperties` + `pattern`
* ✅ ปิดแผลวันนี้ และถูกที่สุดถ้าไม่มีใครส่งจริง
* ❌ **ขัดนิยาม breaking ของ ADR-0006 ตรงตัว** — และสองรีโปที่ pin `execution/v1` อาจตกโดยที่เราไม่รู้
* ❌ ถ้าทำแล้วใครตก เราจะได้บทเรียนเดียวกับ `event/v1 v1.8.1` ที่ ratchet กลืนตัวเอง แต่คราวนี้เป็นฝั่งเราทำให้คนอื่นตก

### C. เปิด `artifact/v2` พร้อมรูปที่ถูก · `v1` อยู่ต่อจน consumer ย้ายครบ
* ✅ ตรงกติกา ADR-0006 ข้อ A เป๊ะ
* ✅ `v2` ใส่ `covers` แบบเดียวกับ `payload_digest` ได้เลยตั้งแต่วันแรก
* ❌ เปิด major ใหม่เพื่อช่องเดียว บน contract ที่ยังไม่มีใคร pin ตรง ๆ — ราคาสูงและเร็วเกินไป
* ❌ ไฟล์ซ้ำทั้ง directory ตามข้อเสียที่ ADR-0006 ข้อ A ยอมรับไว้เอง

### D. ลงครึ่งที่ไม่ breaking วันนี้ + เข้าคิว `v2` ไว้ โดยถาม consumer ก่อน ⭐
* ✅ **ประกาศความหมายของความว่าง** ที่ `description` — *ไม่มี `checksum` = ไม่ได้อ้างว่าเนื้อตรง ไม่ได้แปลว่าเนื้อตรง* · เป็นเอกสาร ไม่ใช่ validation จึงไม่ breaking ([ADR-0006](0006-contract-versioning.md) ลิสต์ "ไม่ breaking")
* ✅ **เพิ่ม `covers` เป็น optional** — เพิ่ม optional field ไม่ breaking · ผู้ผลิตที่อยากพูดความจริงเรื่องขอบเขตทำได้ทันทีโดยไม่ต้องรอ `v2`
* ✅ **เขียน `⚠️` ที่ตัวช่องว่า `{}` และ `{value}` ยังผ่านอยู่ และมันไม่ใช่หลักฐาน** — ผู้อ่านรู้ตัว แทนที่จะเชื่อผิด
* ✅ **ถามเจ้าของ `devfactory-core` และ `agent-builder-dsh-poc` ผ่าน issue** ว่าส่ง `artifacts[].checksum` อยู่ไหม และรูปไหน — คำตอบนั้นคือสิ่งที่ทำให้ B หรือ C ตัดสินได้ด้วยหลักฐานแทนการเดา
* ❌ **แผลยังเปิดอยู่ระหว่างนี้** · ของที่ได้คือผู้อ่านรู้ตัว ไม่ใช่ validator ปฏิเสธ — และสองอย่างนี้ไม่ใช่สิ่งเดียวกัน
* ❌ มีขั้นที่ขึ้นกับทีมอื่นตอบ ซึ่งอาจไม่ตอบ

### E. แก้นิยาม breaking ของ ADR-0006 ให้ยกเว้น "การปิดรูปที่ใช้งานจริงไม่ได้"
* ✅ ทำให้ B ถูกกติกาทันที
* ❌ **เป็นการแก้กฎเพื่อให้สิ่งที่กฎห้ามกลายเป็นถูก** · ถ้ายกเว้นนี้มีอยู่ ใครก็เถียงได้ว่ารูปของตัวเองก็ "ใช้งานจริงไม่ได้"
* ❌ `guarantees` ของ ADR-0006 คือของที่ consumer พิง — ผ่อนมันเพื่อความสะดวกรอบเดียว คือราคาที่จ่ายยาว

### F. รอผู้ผลิตรายแรกที่ส่ง `checksum` จริง
* ❌ ช่องเปิดมาสองเดือนแล้ว และอาจมีผู้ผลิตอยู่แล้วผ่าน `execution/v1` — หลัก "รอรายแรก" คุมการ *สร้าง* ฟิลด์ ไม่ใช่ฟิลด์ที่เปิดค้างและอาจมีคนใช้แล้ว ([ADR-0033](0033-resource-must-carry-its-own-scope.md) ปฏิเสธข้อนี้ด้วยเหตุผลเดียวกัน)

## Decision

**รับ D** — เคาะ 2026-10-17 · ลงครึ่งที่ไม่ breaking เป็น `artifact/v1` `v1.1.0` และเข้าคิว `v2` ไว้โดยต้องถาม consumer ก่อน

**เหตุผล:** คำถามที่ตัดสินเรื่องนี้ไม่ใช่ *"รูปไหนถูก"* (รูปที่ถูกคือรูปของ `payload_digest` และเรารู้แล้ว) แต่เป็น *"วันนี้มีใครส่งรูปเก่าอยู่หรือไม่"* — และ **เราตอบคำถามนั้นเองไม่ได้** เพราะ payload อยู่ที่ runtime ของทีมอื่น · D เป็นทางเดียวที่เดินหน้าได้โดยไม่ต้องเดาคำตอบนั้น และไม่ปล่อยให้ผู้อ่านเชื่อผิดระหว่างรอ

**ที่ไม่เลือก B** — ไม่ใช่เพราะกลัว แต่เพราะ ADR-0006 เขียนนิยามไว้ชัดและเราเพิ่งอ้างนิยามนั้นเองใน `v1.4.0` เมื่อไม่กี่ชั่วโมงก่อนเพื่ออธิบายว่าทำไม `payload_digest` ไม่ breaking · **ใช้กฎข้อเดียวกันสองมาตรฐานในวันเดียว คือการทำให้กฎนั้นไม่มีความหมาย**

**Authority:** Monthop Champaruang — Platform Owner / Architecture Authority of `agent-platform`

### กฎที่เสนอให้ตีพิมพ์ (ถ้ารับ D)

1. **ไม่มี `checksum` = ไม่ได้อ้างว่าเนื้อตรงกับที่ผลิต ไม่ได้แปลว่าเนื้อตรง** — ผู้บริโภคที่เทียบ checksum *เฉพาะเมื่อมี* จะผ่านทุก artifact ที่ไม่ส่งมา ซึ่งคือทางที่น่าจะถูกใช้มากที่สุด (ถ้อยคำตามรูปของ `policy/v1` `Request.consent` และ `approval/v1` `payload_digest`)
2. **`checksum` ที่ไม่มี `algorithm` ไม่ใช่หลักฐาน** — ตรวจไม่ได้ว่าถูกหรือผิด · consumer ต้องถือว่า *ไม่มี checksum* ไม่ใช่ *checksum ผ่าน*
3. **`checksum: {}` ไม่ใช่ "ยังไม่คำนวณ"** — ถ้ายังไม่คำนวณ ให้ไม่ส่งช่องนี้ · วัตถุว่างคือการประกาศว่ามีโดยไม่มี
4. **`covers` (optional, `minItems: 1`) ประกาศว่าแฮชคลุมอะไร และต้องเป็นสิ่งที่คำนวณจริง** — ไม่มี `covers` = ไม่ได้ประกาศขอบเขต ไม่ได้แปลว่าคลุมทั้ง artifact · ถ้าลำดับมีผลต่อค่าแฮช ลำดับในลิสต์ต้องเป็นลำดับที่ป้อนจริง ([ADR-0025](0025-provider-switch-and-what-identity-covers.md))
5. **`checksum` ที่ไม่มี `uri` ไม่มีตัวชี้ว่าคลุมอะไร** — เป็นแฮชของสิ่งที่ใบนี้ไม่ได้บอกว่าอยู่ไหน · `v2` ควรบังคับความสัมพันธ์นี้ `v1` บังคับไม่ได้
6. **การบังคับทั้งสี่ข้อข้างบนเป็นงานของ `artifact/v2`** — `v1` ได้แค่เอกสารกับช่อง optional และใบนี้ไม่แกล้งว่าเอกสารเท่ากับด่าน

### `artifact/v1` `v1.0.0` → `v1.1.0` — ไม่ breaking

เพิ่ม optional field (`covers`) · เพิ่มคำกำกับ · **ไม่แตะ `required` ไม่เพิ่ม `pattern` ไม่เพิ่ม `additionalProperties`** ตามนิยามของ ADR-0006

### พิสูจน์ว่าไม่ breaking — รวมทางที่ผู้ผลิตใช้จริง

ชุดตรวจ 15 เคส `FAIL=0` · เจ็ดเคสแรกคือ **ทุกรูปที่ valid ก่อน `v1.1.0` ต้องยัง valid**

```text
B1 ไม่มี checksum เลย            valid ✅     B5 algorithm อย่างเดียว          valid ✅
B2 checksum: {}                 valid ✅     B6 สองช่องแบบเดิม ไม่มี covers    valid ✅
B3 {value} ไม่มี algorithm       valid ✅     B7 ช่องเกินในบล็อก              valid ✅
B4 {value: ''}                  valid ✅
C1 covers หนึ่งรายการ            valid ✅     C3 covers: []                  invalid ✅
C2 covers หลายรายการ             valid ✅     C4 covers: ['']                invalid ✅
                                            C5 covers ไม่ใช่ array           invalid ✅
R1 ขาด artifact_id              invalid ✅   R2 type นอก enum               invalid ✅
```

และเคสที่แบกคำกล่าวอ้างนี้ไว้จริง — **ทางที่ผู้ผลิตเอื้อมถึง `artifact/v1` คือผ่าน `execution/v1`** จึงต้องตรวจทางนั้นด้วย ไม่ใช่ตรวจแต่ตัว `artifact` เดี่ยว ๆ

```text
execution/v1 (context ครบ 4 id) + artifacts[0].checksum = {value: "abc"}
→ valid ✅  ไม่ breaking
```

**ถ้าตรวจแต่ `artifact/v1` เดี่ยว ๆ ก็จะเป็นการวัดไม่ตรงจุดที่ของพัง** ซึ่งเป็นความผิดเดียวกับที่ใบนี้รายงานไว้ข้างบนเรื่องทะเบียน · ชุดตรวจอยู่ใน scratchpad ไม่ได้ commit ตาม [ADR-0011](0011-conformance-automation.md) — ตัวเลขนี้ตรวจซ้ำจากรีโปไม่ได้ ต้องรันเอง

## Consequences

* **แผลยังเปิดถึง `v2`** — `{}` และ `{value}` ยัง valid · ใบนี้ซื้อ *ผู้อ่านรู้ตัว* ไม่ได้ซื้อ *validator ปฏิเสธ* และเขียนไว้ตรง ๆ ว่าสองอย่างนี้ต่างกัน
* **ต้องถามสองรีโปก่อนถึงจะตัดสิน `v2` ได้ด้วยหลักฐาน** — `devfactory-core` · `agent-builder-dsh-poc` · ช่องทาง issue เท่านั้น ([ADR-0011](0011-conformance-automation.md) และกติกาของรีโปนี้ห้ามแตะ checkout ของทีมอื่น)
* **ทะเบียนมีข้อบกพร่องที่ใบนี้ไม่ได้แก้** — `architecture/consumers.md` นับ pin ที่ประกาศ ไม่ได้นับการเอื้อมถึงผ่าน `$ref` · คนอ่านตัวเลข "ยังไม่มีใคร" แล้วสรุปว่าแก้ได้ฟรี ซึ่งผมทำเองมาแล้วในรอบนี้ · **เปิดเป็นเรื่องถัดไป ไม่ใช่ปล่อยเงียบ** — ทางที่น่าจะถูกคือคอลัมน์ "เอื้อมถึงผ่าน" ที่คำนวณจาก `$ref` ไม่ใช่จากคำประกาศ
* **`drift check` ตรวจข้อ 1–5 ไม่ได้** — เป็นความหมาย ไม่ใช่รูป · ตรวจได้ที่ CI ของผู้ผลิตเท่านั้น เหมือน ADR-0030 ถึง ADR-0035
* **`payload_digest` ใน `approval/v1` ไม่ได้รอใบนี้** — มันบังคับ `covers` ไปแล้วเพราะเป็นช่องใหม่ · ผลคือรีโปเดียวกันจะมีสองมาตรฐานของ checksum อยู่พักหนึ่ง (`approval` เข้ม · `artifact` หลวม) **ซึ่งเป็นสภาพที่ต้องยอมรับอย่างรู้ตัว ไม่ใช่สิ่งที่มองไม่เห็น**
