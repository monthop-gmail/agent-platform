# ADR-0035: ทุกช่องที่ผูกใบอนุมัติเข้ากับงานเป็น id ล้วน — และ digest ที่ไม่บอกขอบเขตของตัวเองคือแฮชที่เชื่อไม่ได้

**Status:** **Accepted** (2026-10-13)
**อัปเดต:** 2026-10-17 — รีวิวจากนอกทีมจับได้สองแผลที่ใบนี้เขียนเอง และข้อหนึ่งที่การแก้ยังปิดไม่ถึง · Amendment 1
**Date:** 2026-10-13
**Depends on:** [ADR-0006](0006-contract-versioning.md) กฎข้อ 1 · [ADR-0019](0019-execution-records-its-approval.md) · [ADR-0023](0023-frozen-bindings-and-identity.md) · [ADR-0025](0025-provider-switch-and-what-identity-covers.md) · [ADR-0030](0030-the-field-nobody-named.md) · [ADR-0033](0033-resource-must-carry-its-own-scope.md)
**Blocking:** `contracts/approval/v1` → `v1.4.0`

## Context

`ai-tools-mcp` ขอ **field ระดับ platform หนึ่งช่อง** ใน `approval/v1` สำหรับ digest ของสิ่งที่จะรันจริง (`ho-9694f90d` · `dis-514ae7a7` `seq 79` ข้อ 4) · ชื่อและชนิดยกให้เราตัดสิน · ขอ optional ไม่ขอให้บังคับ ไม่ขอให้แก้ `guarantees` ไม่ขอให้เพิ่มค่าใน `Decision` และไม่ขอให้เรานิยามวิธีคิด digest

คำถามที่เขาขอให้ตัดสินมีข้อเดียว: **เกณฑ์ ADR-0006 กฎข้อ 1 ที่เราใช้กับ `correlation_id` ใช้กับ digest ได้เหมือนกันหรือไม่**

### อาการ — ทุกช่องที่ผูกใบเข้ากับงาน เป็น id ล้วน ๆ

ไล่ `approval/v1` ทั้งไฟล์ · ช่องที่ผูกใบเข้ากับสิ่งที่มันอนุมัติมีสี่ช่อง และ **ไม่มีช่องใดแตะเนื้อ**

```text
subject.type + subject.id    ชนิดและ id ของสิ่งที่ถูกอนุมัติ
execution_id                 id ของการรัน
policy_id                    id ของนโยบายที่ทำให้ต้องขออนุมัติ
correlation_id               id ของสายงาน
                             ↑
          ทั้งสี่ช่องตอบว่า "อนุมัติให้เรื่องไหน"
          ไม่มีช่องใดตอบว่า "อนุมัติให้ทำอะไรด้วยค่าอะไร"
```

**ใบที่ผูกด้วย id อนุมัติ *คำขอ* · ใบที่ผูกด้วย digest อนุมัติ *สิ่งที่จะเกิดขึ้น*** — สองอย่างนี้ต่างกันทันทีที่ argument เปลี่ยนระหว่างทางระหว่างที่ใบยังใช้ได้

### หลักฐานที่ผู้ขออ้าง และสิ่งที่เราตรวจได้จริง

`seq 79` อ้าง `care-agent-platform` ที่ `dis-a84b7a8e` `seq 6` ว่าใบที่อนุมัติ `reboot node A` ถูกเอาไปรันคำสั่งอื่นบน node B ได้จริงใน production ของเขา

⚠️ **เราเปิดกระทู้นั้นจาก `ws-001` ไม่ได้ — id ไม่ resolve** · ใบนี้จึงนับข้อนั้นเป็น **รายงานที่อ้างถึง ไม่ใช่หลักฐานที่เรายืนยันเอง** ตามนิสัยเดียวกับที่ ADR-0033 แยก "ยืนยันเองแล้ว" ออกจาก "เชื่อรายงาน"

**และการตัดสินใบนี้ไม่ได้พิงข้อนั้น** — เหตุผลเชิงโครงสร้างยืนอยู่บนไฟล์ของเราเองทั้งหมด ดังข้อถัดไป

### สาเหตุเชิงโครงสร้าง — และรีโปนี้บันทึกบั๊กของ digest ไว้แล้วหนึ่งใบ

`model/v1` `inference.schema.yaml` `platform_rules` เขียนไว้ตั้งแต่ [ADR-0023](0023-frozen-bindings-and-identity.md):

> **"checksum ที่คำนวณจาก manifest อย่างเดียว บอกได้แค่ว่า manifest เหมือนกัน ไม่ได้บอกว่าสิ่งที่รันเหมือนกัน — catalog เปลี่ยนแล้ว checksum เท่าเดิมแต่รันคนละ model ถ้า identity ไม่ครอบ binding คำว่า reproducible จะไม่มีความหมาย"**

และ [ADR-0025](0025-provider-switch-and-what-identity-covers.md) ต่อว่า identity ต้องครอบ **ทั้งชุดที่ถูกแช่แข็งรวมลำดับ** เพราะ *"สลับลำดับ = พฤติกรรมต่างกันภายใต้ความล้มเหลวเดียวกัน"*

**แผลเดียวกันนี้ย้ายมาอยู่ที่ใบอนุมัติแบบคำต่อคำ:**

```text
digest ที่คลุมแค่ชื่อ tool        → เปลี่ยน argument ได้ แฮชเท่าเดิม
digest ที่คลุม argument ไม่ครบ    → เปลี่ยนช่องที่ไม่ถูกคลุมได้ แฮชเท่าเดิม
digest ที่ไม่สนลำดับ              → สลับลำดับได้ แฮชเท่าเดิม
                                   ↑
                  ทั้งสามทาง payload valid · CI เขียว · ใบอนุมัติดู "ผูกกับเนื้อ" แล้ว
```

**แฮชที่ไม่บอกว่าตัวเองคลุมอะไร ให้ความมั่นใจมากกว่าที่มันมีสิทธิ์ให้** — และนี่แรงกว่าการไม่มีช่องเลย เพราะไม่มีช่องคือรู้ตัวว่าไม่มี · มีช่องที่ขอบเขตไม่ประกาศคือเชื่อว่ามีแล้ว

### และความว่างต้องมีความหมายที่ประกาศไว้

field เป็น optional ตามที่ผู้ขอขอ · แต่ถ้าไม่ประกาศว่า "ไม่มี" แปลว่าอะไร ผู้ตรวจที่เขียนกฎแบบ *"ถ้ามี digest ให้เทียบ"* จะ **ผ่านทุกใบที่ไม่ส่ง digest มา** — คือผ่านทางที่น่าจะถูกใช้มากที่สุด

รีโปนี้ปิดรูปนี้ไว้แล้วหนึ่งที่ และยืมถ้อยคำมาได้ตรง ๆ (`policy/v1` `policy-decision.schema.yaml:135`):

> **"ไม่มี field นี้ = ผู้เรียกไม่ได้ส่งมา ไม่ได้แปลว่าไม่ต้องมีความยินยอม"**

## Options

### A. ปัด — ให้ไปขึ้น RFC ที่ `devfactory-core` ก่อน

* ✅ ปลอดภัยที่สุดต่ออำนาจของต้นทาง · ผู้ขอบอกเองว่าถ้าต้องขึ้น RFC เขาจะไปเปิดเรื่องเอง
* ❌ **ไล่หกประเภทของ Rule 2 แล้วไม่เข้าข้อไหนเลย** — ไม่ลบ ไม่เปลี่ยนชื่อ ไม่เพิ่มค่าใน `Decision` ไม่ลดหรือถอน guarantee ไม่พลิก `required` ↔ optional (ช่องใหม่) ไม่เปลี่ยนความหมายของค่าที่มีอยู่
* ❌ **ข้อที่หกของ Rule 2 คือ "เปิดทางให้ execution เดินได้โดยไม่มี `APPROVE`" · digest ทำตรงกันข้าม** — มันทำให้ขอบเขตของ `APPROVE` หนึ่งใบ *แคบลง* · ปัดด้วยเหตุนี้คือใช้กฎกลับทาง
* ❌ `correlation_id` อยู่ในลิสต์กฎข้อ 1 และอยู่ในไฟล์นี้แล้วพร้อมคำกำกับว่าเพิ่มเองได้ · ปัดคือกลับคำของตัวเองโดยไม่มีหลักฐานใหม่

### B. รับ และใส่เป็นสตริงแฮชเปล่า

* ✅ เล็กที่สุด · ผู้ขอได้ของที่ขอพอดี ไม่เกิน
* ❌ **แยก sha256 จาก sha512 ไม่ออก** — ย้ายอัลกอริทึมวันหน้าต้องเดาจากความยาว หรือเพิ่ม field ที่สองแล้วมีสองรูปอยู่ในสัญญาเดียว
* ❌ **ไม่ตอบคำถามว่าแฮชคลุมอะไร** ซึ่งเป็นคำถามเดียวที่ทำให้แฮชมีความหมาย · เท่ากับส่งแผลของ ADR-0023 ต่อไปทั้งก้อน
* ❌ `artifact/v1.checksum` มีรูป `{algorithm, value}` อยู่แล้ว — ใส่สตริงเปล่าคือสร้างรูปที่สองสำหรับของชนิดเดียวกันในรีโปเดียวกัน

### C. รับ · รูป `{algorithm, value}` ตาม `artifact/v1.checksum` + บังคับให้ประกาศขอบเขตที่มันคลุม ⭐

* ✅ **ตอบคำถามที่ผู้ขอถามมาตรง ๆ** — Rule 1 ใช้ได้ และบอกชื่อ field กับเวอร์ชันให้ ADR-0009 อ้างได้
* ✅ **ปิดแผลที่รีโปนี้บันทึกไว้เองแล้ว ก่อนที่มันจะถูกย้ายมาที่ใบอนุมัติ** — `covers` ทำให้ "แฮชนี้คลุมอะไร" อ่านได้จากตัวค่า ซึ่งเป็นสิ่งเดียวที่ทั้งสามทางของความล้มเหลวต้องการ
* ✅ **ใช้รูปที่มีอยู่แล้วในรีโป** ไม่สร้างคำศัพท์ใหม่ — `{algorithm, value}` จาก `artifact/v1` · `minItems: 1` สำหรับลิสต์ที่ว่างแปลว่าว่าง · ถ้อยคำ "ไม่มี ≠ ไม่ต้องมี" จาก `policy/v1`
* ✅ ไม่ breaking — ช่องใหม่ optional · `required` เจ็ดช่องไม่ขยับ · `guarantees` ไม่ขยับ · `$defs.Decision` ไม่ขยับ
* ✅ **ทำให้เกณฑ์ A1 ของผู้ขอวัดได้** — วันนี้ `CRITERIA.md` รายงาน A1 สี่ทางเป็น `วัดไม่ได้` เพราะไม่มีช่อง
* ❌ **platform บังคับเนื้อของ `covers` ไม่ได้** — เราไม่รู้จักโดเมนของผู้ผลิต เหมือนที่ [ADR-0030](0030-the-field-nobody-named.md) ปฏิเสธ enum ให้ `error/v1.details` และ [ADR-0033](0033-resource-must-carry-its-own-scope.md) ปฏิเสธทะเบียน scheme กลาง · บังคับได้แค่ว่า **ต้องมี และต้องตรงกับสิ่งที่คำนวณจริง**
* ❌ validator กลางตรวจได้แค่รูป — ตรวจไม่ได้ว่า `covers` พูดความจริง · ต้องเขียนข้อจำกัดนี้ไว้ในสัญญา ไม่ปล่อยให้คนอ่านเชื่อว่าเครื่องบังคับให้

### D. รับ และบังคับให้ทุกใบต้องมี digest

* ✅ ปิดทางที่ความว่างจะถูกอ่านผิดได้สนิทที่สุด
* ❌ **breaking** ตาม [ADR-0006](0006-contract-versioning.md) — payload ของผู้ผลิตที่มีอยู่ทุกรายตกทันที
* ❌ **ใบอนุมัติที่ไม่มี payload ก็มีจริง** — `subject.type: record` คือบันทึกของโดเมนที่ไม่ได้เกิดจาก job (RFC-0016) · บังคับ digest ให้ของที่ไม่มีอะไรให้แฮชคือบังคับให้ผู้ผลิตกรอกค่าหลอก
* ❌ ผู้ขอไม่ได้ขอข้อนี้ และบอกชัดว่าไม่ขอ · ให้เกินที่ขอโดยแลกกับ breaking เป็นการตัดสินใจแทนคนอื่น

## Decision

**C** — รับคำขอ · `payload_digest` เป็น field ระดับ platform ตาม ADR-0006 กฎข้อ 1 · รูป `{algorithm, value, covers}` · optional · ขึ้นที่ `approval/v1` **`v1.4.0`**

**เหตุผล:** เกณฑ์กฎข้อ 1 ใช้กับ digest ได้ ด้วยเหตุผลรูปเดียวกับ `correlation_id` เป๊ะ — `subject` กับ `execution_id` ทำแทนไม่ได้ เพราะทั้งคู่เป็น id ของ *เรื่อง* ไม่ใช่ของ *เนื้อ* และไล่หกประเภทของ Rule 2 แล้วไม่เข้าข้อไหน · แต่คำขอที่มาถึงขอแค่ "ช่องหนึ่งช่อง" ซึ่งถ้าให้ไปตามตัวอักษรจะเป็นแฮชที่ไม่บอกขอบเขตของตัวเอง — **และรีโปนี้บันทึกบั๊กรูปนั้นไว้เองแล้วใน `model/v1` ว่าแฮชที่คลุมไม่ครบทำให้คำว่า reproducible ไม่มีความหมาย** · เราจึงให้ช่องที่ขอ พร้อมข้อบังคับที่ทำให้มันเชื่อได้ ไม่ใช่ช่องที่ดูเหมือนเชื่อได้

**Authority:** Monthop Champaruang — Platform Owner / Architecture Authority of `agent-platform`

### กฎที่ตีพิมพ์

```text
1. `payload_digest` ผูกใบอนุมัติเข้ากับ *เนื้อ* ของสิ่งที่จะเกิดขึ้น
   ไม่ใช่กับ id ของเรื่อง — ต่างจาก subject / execution_id / correlation_id ทั้งสามช่อง

2. `covers` ต้องประกาศว่าแฮชคลุมอะไร และต้องเป็นสิ่งที่คำนวณจริง
   — ไม่ใช่สิ่งที่อยากให้คนเชื่อว่าคลุม
   แฮชที่คลุมไม่ครบแล้วไม่บอก ให้ความมั่นใจมากกว่าที่มันมีสิทธิ์ให้ (ADR-0023)

3. ถ้าลำดับมีผลต่อค่าแฮช ลำดับใน `covers` ต้องเป็นลำดับที่ป้อนเข้าไปจริง
   — สลับลำดับ = พฤติกรรมต่างกันภายใต้ความล้มเหลวเดียวกัน (ADR-0025)

4. **ไม่มี `payload_digest` = ใบนี้ไม่ได้ผูกกับ payload ใด
   ไม่ได้แปลว่า payload ใดก็ได้**
   ผู้ตรวจที่เทียบ digest เฉพาะเมื่อมี จะผ่านทุกใบที่ไม่ส่งมา
   ซึ่งคือทางที่น่าจะถูกใช้มากที่สุด (รูปเดียวกับ policy/v1 consent)

5. การเปลี่ยน payload หลังอนุมัติ ไม่ใช่การแก้ใบ — ต้องเป็นใบใหม่
   `decision` immutable ตาม guarantee ข้อ 1 · ใช้ `supersedes_approval_id`
   ใบที่แก้ digest ของตัวเองคือใบที่ทำลายเหตุผลที่ตัวเองมีอยู่

6. วิธีคำนวณ digest ไม่ใช่ของสัญญาใบนี้ — เป็นของผู้ผลิต
   platform ไม่รู้จักโดเมนของผู้ผลิต จึงกำหนดให้ไม่ได้และไม่ควร
   (เหตุผลเดียวกับ ADR-0030 `error/v1.details` และ ADR-0033 ข้อ 2)

7. ข้อ 2–6 บังคับได้ที่ผู้ผลิตและผู้ตรวจเท่านั้น
   validator กลางตรวจได้แค่ว่ารูปถูก — ตรวจไม่ได้ว่า `covers` พูดความจริง
   เขียนข้อจำกัดนี้ไว้ในสัญญา ไม่ปล่อยให้คนอ่านเชื่อว่าเครื่องบังคับให้
```

### `approval/v1` `v1.3.1` → `v1.4.0` — ไม่ breaking

เพิ่ม `payload_digest` เป็น optional · **ไม่แตะ `required` ทั้งเจ็ดช่อง ไม่แตะ `guarantees` ไม่แตะ `$defs.Decision` ไม่ขยับ `semantics_version`**

`semantics_version` ยังเป็น `1.5` เพราะ **นี่ไม่ใช่ semantics ของต้นทาง** — เป็น field ระดับ platform ตามกฎข้อ 1 รูปเดียวกับที่ `correlation_id` เข้ามาโดยไม่ขยับ pointer

## Consequences

* **เส้น write/privileged ของ `dis-514ae7a7` ไม่ติดที่ฝั่งเราอีก** — ผู้ขอประกาศไว้ว่าจะไม่เปิดเส้นนั้นจนกว่าจะมีช่องนี้ และจะไม่เปิดแล้วผูกด้วย id ไปก่อน
* **เกณฑ์ A1 สี่ทางของ `ai-tools-mcp` เปลี่ยนจาก `วัดไม่ได้` เป็นวัดได้** · แต่ `covers` เพิ่มทางที่ fail ได้ขึ้นมาใหม่ที่เกณฑ์เดิมยังไม่คลุม — **digest ที่ `covers` ไม่ตรงกับสิ่งที่คำนวณจริง** · ข้อนี้เป็นของเกณฑ์ฝั่งเขา ไม่ใช่ของสัญญาใบนี้ และผมแจ้งไว้ในโพสต์
